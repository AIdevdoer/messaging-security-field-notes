A Key Reset Needs Memory

A reset button feels decisive. In an encrypted messenger, it only works if clients remember which conversation keys were retired and refuse to accept them again.

Trail of Bits described this problem in its October 2025 assessment of X Chat. The reviewed design allowed a client to ask the server to delete an encrypted conversation key after a device was lost or stolen. The next exchange could create a fresh key. The auditors found that a server might later replay an older key because clients did not check whether the returned key had already been reset.

The fix review needs careful wording. Trail of Bits saw a new ratchet-tree component, which can help with post-compromise security, but that implementation was outside the review scope. The report therefore marked the replay finding as undetermined. It did not say the issue was definitely present in the product available in August 2026.

This dated finding is still a useful lesson. Key rotation needs evidence on both sides. A client can store a key generation number, a commitment to previous keys, or another authenticated record that makes an old server response recognizable. Without that memory, a successful reset screen proves only that the request was accepted at that moment.

The original finding and fix-review status are in Trail of Bits' public X Chat assessment. Anyone evaluating a recovery or reset feature should ask one extra question. How does a device know that a key declared dead yesterday cannot quietly return tomorrow?
